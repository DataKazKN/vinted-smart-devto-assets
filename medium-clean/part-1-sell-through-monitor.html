I Built a Vinted Monitor That Tracks What Disappears, Not Just What Exists

Part 1/4 of a developer series about turning Vinted scraping into scheduled reseller monitoring.

Disclosure: I built Vinted Smart Scraper on Apify. Some Apify links may use my referral code.

A normal Vinted search tells you what exists right now. A reseller usually needs the opposite:

What changed since yesterday?

That sounds like a small difference, but it changes the whole scraper design.

One-off exports are easy. Scheduled market monitoring is not. You need stable inputs, a persistent state store, clean diffs, cost caps, and a way to avoid calling every missing item "sold" when Vinted simply changed ranking or hid a page.

❌ The wrong abstraction

My first mistake was thinking like this:

"Users need a Vinted scraper."

That is too broad. Resellers do not only need raw listings. They need a repeatable signal.

  • Export one CSV — ✅ Market monitor: Run the same input every day
  • Count active listings — ✅ Market monitor: Compare snapshots
  • Trust hidden sold pages — ✅ Market monitor: Track missing, likely_sold, reappeared
  • Pull everything — ✅ Market monitor: Cap rows with maxItems
  • Pay for noisy rows — ✅ Market monitor: Emit only changes after baseline
  • Debug manually — ✅ Market monitor: Send summary rows to CSV/API/webhook

That is why the most important mode is not the normal SEARCH. It is SELL_THROUGH_TRACKER.

🧠 Why I do not trust sold pages blindly

I also ran SOLD_ITEMS on the same query:

{
  "mode": "SOLD_ITEMS",
  "query": "nike air force 1",
  "countries": ["fr"],
  "maxItems": 5
}

Live result:

  • Run ID — Value: wvFbmO0HscQits0UV
  • Status — Value: SUCCEEDED
  • Rows emitted — Value: 0
  • Free-tier estimated charge — Value: $0.020

The log showed the reason:

Sold-items endpoint variants returned active listings only.
Returning no rows instead of false sold items.

That is exactly the kind of boring defensive behavior I want.

  • Vinted returns active listings from a sold endpoint — Bad scraper behavior: ❌ Mark active items as sold | Safer behavior: ✅ Return zero rows
  • Item disappears for one run — Bad scraper behavior: ❌ Claim it sold | Safer behavior: ✅ Mark missing, low confidence
  • Item stays missing across runs — Bad scraper behavior: ✅ Increase confidence | Safer behavior: ✅ Use missingRunsThreshold

💸 Cost guardrails

With current Free-tier event pricing:

start = $0.020
row = $0.002

The test charges would be:

  • Search snapshot — Rows: 8 | Estimated Free-tier charge: $0.036
  • Sell-through baseline — Rows: 9 | Estimated Free-tier charge: $0.038
  • Scheduled second pass — Rows: 2 | Estimated Free-tier charge: $0.024
  • Sold explicit check — Rows: 0 | Estimated Free-tier charge: $0.020

The practical rule:

  • Inspect all current inventory — First run: ✅ emitActiveItems: true | Scheduled run: ❌ usually too noisy
  • Daily changes only — First run: ❌ not enough baseline | Scheduled run: ✅ emitActiveItems: false
  • Webhook / Telegram — First run: ✅ keep emitRunSummary: true | Scheduled run: ✅ keep emitRunSummary: true

Start with maxItems: 100. Only move to 300 after one run proves the query is useful.

⚠️ Limits

This is not magic.

  • "Missing means sold" — Reality: ❌ No. Missing can mean hidden, removed, reranked, moderated, or sold.
  • "Sold pages are always reliable" — Reality: ❌ Not in my tests. Some endpoint variants returned active listings.
  • "More countries is always better" — Reality: ❌ Current cap is 5 countries per run for stability.
  • "Schedule everything hourly" — Reality: ❌ You pay per start and per emitted row. Start daily.
  • "This guarantees profit" — Reality: ❌ It only gives better market data.

}

That is the difference between scraping Vinted once and monitoring a resale market every day.
