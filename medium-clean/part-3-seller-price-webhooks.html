Seller Watchlists, Price Drops, and Webhooks: The Vinted Signals I Actually Schedule

Part 3/4 of a developer series about turning Vinted scraping into scheduled reseller monitoring.

Disclosure: I built Vinted Smart Scraper on Apify. Some Apify links may use my referral code.

After testing sell-through and country comparison, I wanted to check two smaller signals: 1. Seller profiles. 2. Exact listing price history. Both are useful, but they are not equal. Seller profiles are good for watchlists. Price tracking is good for exact item URLs.

I ran both live on June 4, 2026 with Vinted Smart Scraper.

🧠 Why these signals matter

Most Vinted automation starts with a broad search:

query -> results -> CSV

That is useful once. But resellers eventually ask more specific questions:

Is this seller consistently interesting?
Did this exact item drop?
Did this watched item disappear?
Should I get alerted now or ignore it?

Those are not the same job. That is why this part is about smaller signals. They do not look as impressive as a big export, but they are the signals that make a scheduled workflow useful.

🧩 Seller profile is not item monitoring

Before the live run, I separated the workflows:

  • Seller watchlist — Best signal: Seller activity and profile stats | Bad use: Exact price drops
  • Price tracking — Best signal: Exact item URL history | Bad use: Discovering new items
  • Sell-through tracker — Best signal: Query/listing disappearance | Bad use: Seller reputation
  • Sold-items page — Best signal: Explicit sold evidence when available | Bad use: Assuming every missing item is sold

This matters because a single "Vinted monitor" can easily become confusing. The user should know what each mode is answering.

🔍 What this profile tells me

This row is not an "opportunity" by itself. It is a filter.

  • rating — Live value: 1 | How I use it: Weak trust signal, inspect manually
  • ratingCount — Live value: 11 | How I use it: Enough history to avoid treating it as brand new
  • itemCount — Live value: 1 | How I use it: Not currently a large active inventory

  • followerCount — Live value: 3 | How I use it: Not a high-demand seller profile
  • phone verified — Live value: false | How I use it: Not a blocker, but useful context
  • google verified — Live value: true | How I use it: Basic identity signal

For this seller, I would not build a high-frequency monitor. I might still watch exact item URLs if the listing itself looks underpriced. That is the point: profile data helps decide where not to spend monitoring budget.

✅ When seller monitoring helps

  • Does this seller keep listing relevant inventory? — Mode: SELLER_PROFILE
  • Did their shop count change? — Mode: SELLER_PROFILE
  • Did watched items disappear? — Mode: SELL_THROUGH_TRACKER with item URLs
  • Did an exact listing price drop? — Mode: PRICE_TRACK

I would not schedule seller profile checks every 5 minutes. Daily is usually enough unless you are monitoring a very specific seller.

💸 Run 2: exact listing price tracking

For PRICE_TRACK, I used two real item URLs from the search run:

{
  "mode": "PRICE_TRACK",
  "itemUrls": [
    "https://www.vinted.fr/items/9089776821-nike-air-force-1-shadow-unisex-numero-45",
    "https://www.vinted.fr/items/9089774198-nike-air-pegasus-volt-green-neon-eur42-hq5403-700"
  ],
  "trackingStoreName": "devto-series-price-track-2026-06-04",
  "maxConcurrency": 1,
  "requestDelayMs": 500
}

Live result:

  • Run ID — Value: nWdbpqX2JKdZLs1ad
  • Dataset ID — Value: TkFl0ztR6QMXa65MM
  • Status — Value: SUCCEEDED
  • Duration — Value: 359s
  • Rows emitted — Value: 2
  • Free-tier estimated charge — Value: $0.024

This run was slow because Vinted returned several 403s. That is the interesting part. From the run log:

Browser price fallback failed for item 9089776821: timed out after 30000ms
Price unavailable for item 9089776821; history not updated
Resolved item 9089774198 price through browser fallback
Price tracked for item 9089774198: 39.99 EUR (0% drop)

This is exactly the kind of boring log I want in a scraper. Not because timeouts are good. Because the Actor did not corrupt the price history when extraction failed.

🛡️ The important fallback

For the first item, price extraction failed. The Actor returned:

{
  "itemId": 9089776821,
  "currentPrice": null,
  "currency": "EUR",
  "priceHistory": [],
  "priceDropPct": 0,
  "priceUnavailable": true,
  "warning": "Current price could not be extracted; price history was not updated."
}

That is the right failure mode.

  • Price blocked once — Bad behavior: ❌ Write 0 into history | Safer behavior: ✅ Mark priceUnavailable
  • Browser fallback times out — Bad behavior: ❌ Delete previous history | Safer behavior: ✅ Keep history clean
  • API returns 403 — Bad behavior: ❌ Crash whole watchlist | Safer behavior: ✅ Continue to next item

For the second item, the browser fallback worked:

{
  "itemId": 9089774198,
  "currentPrice": 39.99,
  "currency": "EUR",
  "priceHistory": [
    {
      "price": 39.99,
      "date": "2026-06-04T20:27:02.852Z"
    }
  ],
  "priceDropPct": 0
}

The log confirmed it:

Resolved item 9089774198 price through browser fallback
Price tracked for item 9089774198: 39.99 EUR (0% drop)

📊 Two rows, two different meanings

Both rows came from the same run, but they should trigger different actions:

  • 9089776821 — Result: priceUnavailable: true | Action: Keep previous history, retry later
  • 9089774198 — Result: currentPrice: 39.99 | Action: Store history point, compute future drops

This distinction is important for alerts. If a scraper treats "blocked once" as "price is zero", every downstream alert becomes garbage. For a real watchlist, I want this rule:

No extracted price = no price-history mutation

That is less exciting than a fake discount alert, but it is much safer.

🧾 Persistent price tracking contract

The trackingStoreName is the anchor:

{
  "trackingStoreName": "devto-series-price-track-2026-06-04"
}

Use one stable store name per watchlist.

  • daily-af1-watchlist-fr — Good?: ✅ | Why: Stable and specific
  • seller-adwatches-watchlist — Good?: ✅ | Why: Seller-scoped
  • test — Good?: ❌ | Why: Easy to reuse by accident
  • price-track — Good?: ❌ | Why: Too broad
  • New random name every run — Good?: ❌ | Why: No persistent history

The store name is what turns a run into a history. Without it, you are just re-scraping the current price.

🔔 Webhook shape

For scheduled alerts, I would not send the full dataset every time. I would send a compact payload like:

{
  "workflow": "vinted-price-watchlist",
  "itemId": 9089774198,
  "currentPrice": 39.99,
  "priceDropPct": 0,
  "priceUnavailable": false,
  "runId": "nWdbpqX2JKdZLs1ad"
}

Or for unavailable prices:

{
  "workflow": "vinted-price-watchlist",
  "itemId": 9089776821,
  "priceUnavailable": true,
  "action": "do_not_update_history"
}

For Telegram, I would keep it even shorter:

Vinted price watch: 9089774198 still at 39.99 EUR. No drop yet.

And for a failed extraction:

Vinted price watch: 9089776821 price unavailable. History not changed.

The second message is not glamorous, but it prevents bad decisions.

💸 Cost and scheduling guardrails

The live PRICE_TRACK run emitted 2 rows. At the Free pricing available when I ran it:

$0.020 / Actor start
$0.002 / result row

The estimated charge was:

$0.020 + (2 * $0.002) = $0.024

The bigger risk is time, not just row cost. This run took 359s because of fallback behavior. So I would not schedule a huge exact-URL watchlist every few minutes.

  • 1-5 exact URLs — Cadence I would start with: Every few hours | Why: Acceptable if items are high-value
  • 5-20 exact URLs — Cadence I would start with: Daily | Why: Better balance
  • 20-100 URLs — Cadence I would start with: Daily/weekly split | Why: Avoid one slow run blocking everything
  • Broad discovery — Cadence I would start with: Use SELL_THROUGH_TRACKER instead | Why: Exact URLs are the wrong tool

✅ Alert rules I would trust

For price tracking:

  • priceDropPct > 10 — Alert?: ✅
  • priceUnavailable: true once — Alert?: ❌
  • priceUnavailable: true multiple times — Alert?: Maybe, as a health warning
  • New price history point, no drop — Alert?: ❌
  • Exact watched item disappears — Alert?: Use sell-through/missing logic

For seller watchlists:

  • Active item count jumps — Alert?: ✅
  • Seller appears in a profitable query repeatedly — Alert?: ✅
  • Rating count changes — Alert?: Maybe
  • Last seen changes — Alert?: Usually no

The goal is not more alerts. The goal is fewer, better alerts.

✅ What I would schedule

  • Seller profile — Schedule: Daily | Why: Slow enough, useful for seller watchlists
  • Price track 5-20 exact URLs — Schedule: Daily | Why: Good for item-specific monitoring
  • Sell-through query — Schedule: Daily or every few hours | Why: Best market movement signal
  • Sold explicit pages — Schedule: Only when needed | Why: Can return zero by design
